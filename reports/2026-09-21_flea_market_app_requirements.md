# 犬猫フリマ×寄付アプリ 要件定義書（MVP）

**作成日**: 2026-09-21
**作成**: Jobs CEO 統括
**プロジェクト名（仮）**: わけあいっこ（仮称）
**RULES**: Rule 1・2・4 準拠

---

## 0. コンセプト（1行）

> **売る・買うだけで、勝手に保護犬猫支援になるフリマアプリ。**
> トリミングサロンとの物流連携は行わない。運用コストを極限まで抑え、
> 「定期的に細く取引が回る」ことを成功ラインとする。

---

## 1. ターゲットユーザー

| ユーザー種別 | 役割 | 現状の接点 |
|------------|------|-----------|
| 飼い主 | 出品者・購入者（メイン） | 既存フォロワー・BL顧客 |
| 保護団体 | 寄付先・信頼の裏付け・初期出品協力 | 既存フォロワー1名 |
| （将来）企業 | CSR協賛・在庫委託販売 | 現状なし。実績ができてから開拓 |

---

## 2. 提供価値・差別化ポイント（vs メルカリ等汎用フリマ）

```
① 犬種・サイズ特化検索（体重・犬種でグッズを絞り込める）
② 取引ごとに自動で保護団体支援になる（運営が手数料の一部を寄付）
③ 寄付実績の可視化（月次で「〇〇円届きました」を見せる）
```

**やらないこと（意図的なスコープ外）**
- サロンでの受け渡し・クリーニング認証連携（協業コストが重いため見送り）
- 配送の独自インフラ化（既存の匿名配送等をそのまま利用）

## 3. MVP機能一覧

### 必須機能（Phase 1）

| # | 機能 | 概要 |
|---|------|------|
| 1 | 会員登録・ログイン | メール or SNS認証 |
| 2 | 出品機能 | 写真・商品名・カテゴリ・犬種/体重タグ・価格・説明文 |
| 3 | 検索・絞り込み | カテゴリ／犬種／体重帯／エリア／価格帯 |
| 4 | 購入・決済 | クレジットカード決済（決済代行サービス利用） |
| 5 | メッセージ機能 | 出品者⇄購入者の簡易チャット |
| 6 | 寄付表示 | 各商品ページに「この取引の一部が保護団体支援になります」を明示 |
| 7 | 寄付実績ページ | 月次の累計寄付額・団体からの活動報告を掲載 |
| 8 | 評価機能 | 取引後の簡易評価（星＋一言） |

### 後回しでよい機能（Phase 2以降）

```
・サロンでの受け渡し／クリーニング認証（需要が見えてから検討）
・企業スポンサー枠・CSRマッチング寄付
・文脈連動アフィリエイト（在庫がない時の代替商品提案）
・有料の目立たせオプション（掲載順位アップ等）
・データ分析ダッシュボード（犬種×エリア×グッズ種別の集計）
```

## 4. 画面構成（主要画面）

```
① トップ画面（新着出品・カテゴリ一覧・寄付累計額バナー）
② 検索・絞り込み画面
③ 商品詳細画面（写真・説明・寄付表示・購入ボタン）
④ 出品画面（写真アップロード・情報入力）
⑤ メッセージ画面
⑥ マイページ（出品中／購入履歴／評価）
⑦ 寄付実績ページ（団体紹介・累計額・活動報告）
```

---

## 5. 収益モデル

```
① 取引手数料：出品者から5〜8%程度
   → 一部を運営費、一部を寄付原資に充当
② （将来）企業CSR協賛・在庫委託販売
③ （将来）文脈連動アフィリエイト
④ （将来）有料の目立たせオプション
```

**Phase 1では①のみで良い。** 収益の柱を増やすのは、実際の取引量が見えてから。

---

## 6. 寄付の仕組み（実装方式・注意点）

**個々の取引ごとに買い手の代金の一部を団体へ直接送金する設計は避ける**
（資金決済に関する規制に触れる可能性があるため）。

```
運営が手数料としていったん受け取る
→ 月末等にまとめて運営の意思で団体へ寄付する
```

この形にすることで、個別取引の分割送金という複雑な仕組みを持たずに済む。

---

## 7. 非機能要件

| 項目 | 方針 |
|------|------|
| 開発体制 | AIアシスト開発を活用し、少人数（メンバー主導）で構築 |
| 運用コスト | サーバー費・決済手数料程度に抑える。物流インフラは持たない |
| スケール想定 | 初期は数十〜数百ユーザー規模を想定。無理な先行投資はしない |
| セキュリティ | 決済は自社実装せず、決済代行サービス（Stripe等）を利用 |

## 7.5 開発言語・技術スタック

**将来的に外部IT企業へ運用を引き継ぐこと**を前提に、
「採用市場の厚さ＝引き渡しのしやすさ」を最優先で選定する。

### 推奨スタック

```
フロントエンド（アプリ本体）： React Native（TypeScript）
バックエンド／インフラ　　　： Firebase または Supabase
決済　　　　　　　　　　　　： Stripe 等の決済代行サービス
```

### 選定理由

| 観点 | React Native（TypeScript） | 備考 |
|------|---------------------------|------|
| 引き渡しやすさ | ◎ | TypeScript/JavaScriptエンジニアの母数は国内外で最大級。どのIT企業でも対応可能な確率が高い |
| 開発効率 | ◎ | iOS/Androidを1つのコードベースで開発でき、少人数運用に向く |
| AI開発との相性 | ◎ | AIコーディングツールが最も強い言語群の一つ。メンバー主導のAI活用開発と噛み合う |
| 将来性 | ◎ | スタートアップの定番構成であり、標準的な形として引き継ぎ先にも理解されやすい |

### 比較検討した他の選択肢

| 選択肢 | 引き渡しやすさ | 却下・保留の理由 |
|--------|--------------|-----------------|
| Flutter（Dart） | ○ | 良好だが、TypeScript/JSほどの採用市場の厚みはない |
| ネイティブ（Swift＋Kotlin） | △ | iOS/Android別々の実装が必要で、2職種分の採用・保守コストがかかる |
| ノーコードツール | △ | 開発は最速だが、専用プラットフォームに縛られ、外部IT企業への引き渡しに不向き |

### バックエンド選定の補足

Firebase／Supabaseはいずれも認証・データベース・ストレージが最初から揃っており、
小規模運用であれば無料枠中心で賄える。エンジニア人口も多く、引き渡し先を選ばない。

## 8. 成功基準（KPI）

**「大きく儲ける」ではなく「細く定期的に回る」ことを成功ラインとする。**

| 指標 | 目安（初期） |
|------|-------------|
| 月間出品数 | 10件以上 |
| 月間成約数 | 3〜5件以上 |
| 月次寄付額 | 継続的に発生していること（金額の大小より継続性） |
| リピート出品者 | 1名以上（サイズアウトの度に使ってもらえるか） |

## 9. 立ち上げ手順（開発前の検証ステップ）

いきなり本格開発せず、以下で需要を検証してから着手する：

```
① Instagram/LINE公式アカウントで簡易的な「ゆずりますコーナー」を試す
② 保護団体の方に初期出品への協力を依頼
③ 既存フォロワー（飼い主）に告知し、数件でも取引が発生するか確認
④ 実際に動きが見えたら、上記MVP機能でアプリ本開発に着手
```
